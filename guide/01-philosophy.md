# 01 - 核心理念：为什么用代码做 PPT

## 传统 PPT 的痛点

大多数人做 PPT 的流程是：打开 PowerPoint → 选个模板 → 拖拽文字框和图片 → 调整位置和大小 → 导出。

这个流程有几个根本性问题：

### 1. 设计意图不可追溯

你花了两小时调好一页的排版，第二天想做类似的一页，发现完全记不清当时怎么调的。"这个渐变的角度是多少？" "这个字号是36还是40？" 全凭感觉。

### 2. 版本管理是灾难

`方案v3_改改_最终版_老师改后_真的最终.pptx` —— 这不是段子，这是现实。你无法精确知道两个版本之间到底改了什么。

### 3. 风格一致性靠肉眼

15 页 PPT，每页的标题大小、颜色、位置要一致，全靠手动对齐。改一页的风格，其他页不会自动跟着变。

### 4. 迭代成本高

设计师出了 3 个方案，你选了方案 B，然后想在 B 的基础上融合 A 的某个元素——这在传统流程里几乎意味着重做。

### 5. 知识无法沉淀

项目做完了，下一次做 PPT 还是从零开始。你不记得上次学到了什么技巧，什么配色方案有效，什么排版踩了坑。

## 工程师的解法

软件工程早就解决了这些问题：

| 传统 PPT 的痛点 | 软件工程的解法 | 我们的实践 |
|----------------|-------------|-----------|
| 设计意图不可追溯 | 代码即文档 | Prompt 就是设计意图的文字表达 |
| 版本管理混乱 | Git | 每页独立提交，commit message 记录改动 |
| 风格一致性靠肉眼 | 配置文件 + 模板 | CLAUDE.md 统一视觉规范 + 参考图机制 |
| 迭代成本高 | 修改代码重新编译 | 修改 Prompt 重新生成 |
| 知识无法沉淀 | 文档 + Code Review | 制作记录 + Prompt 经验库 |

## 核心概念：Prompt as Design

在这套方法论中，**Prompt 就是设计稿**。

传统流程里，设计师用 Figma/Sketch 画设计稿，然后开发者照着实现。我们的流程是：**Prompt 就是设计稿，AI 模型就是实现者**。

一个好的 Prompt 应该包含：
- **布局描述**：什么元素在什么位置
- **视觉风格**：色调、质感、光影
- **文字内容**：具体文案、字体大小、颜色
- **情绪基调**：这页想传达什么感觉
- **约束条件**：什么不能被遮挡，什么必须保持一致

这段文字就是"源代码"，可以被版本控制、被复用、被迭代优化。

## 核心概念：参考图 as 配置

参考图在这套方法论中扮演"配置文件"的角色。它不是让 AI 照抄，而是提供：

- **风格锚定**：确保新生成的页面和已有页面视觉一致
- **布局参考**：导航栏位置、文字区域、主体元素比例
- **基线校准**：已被确认的页面成为后续页面的基准

这类似于 CSS 框架——你不用从零写样式，而是在已有基础上做增量修改。

## 核心概念：候选制 as A/B Testing

每次不是生成 1 张图，而是并发生成 3 张。

这不是浪费，而是借鉴了 A/B Testing 的思路：

1. **降低单次决策的风险** — 不用纠结这张到底行不行，3 张里选最好的
2. **探索设计空间** — 同一个 Prompt，AI 的随机性会带来意想不到的好方案
3. **建立质量基线** — 如果 3 张都不行，说明 Prompt 有问题；如果 1 张很好 2 张一般，说明方向对了但需要微调

## 适用场景

这套方法最适合：

- **视觉密集型 PPT**：需要高质量背景、3D 渲染、概念艺术风格
- **需要大量迭代的场景**：比赛、提案、重要汇报
- **有明确风格要求的项目**：品牌一致性、主题贯穿
- **多人协作的 PPT 项目**：需要分工并行、保持一致

不太适合：

- **纯文字 PPT**：用模板就够了
- **一次性简单场景**：花 5 分钟做个内部分享的 PPT
- **强交互设计**：需要动画、视频嵌入的场景
