# 04 - 项目管理方法

## 核心思想：PPT 项目就是软件项目

一个 15 页的 PPT 项目，如果需要多轮迭代，其复杂度不亚于一个小型软件项目。我们用软件工程的项目管理方法来驯服这个复杂度。

## 三个核心文档

### 1. CLAUDE.md — 项目规范（相当于 Architecture Doc）

这份文档有三个读者：
- **你自己** — 下次打开项目时，快速回忆项目上下文
- **AI 协作者** — Claude/Cursor 每次对话都会读这个文件，确保行为一致
- **协作者** — 如果有人接手你的项目，这就是入口

核心章节：
1. 项目概述（做什么、给谁做）
2. 目录结构（文件在哪）
3. 视觉风格规范（色调、质感、字体）
4. 工作流（标准操作流程）
5. 重要规则（边界和约束）
6. Prompt 经验（持续积累）

**关键原则：这个文件是活的，随着项目推进持续更新。**

### 2. progress.md — 进度追踪（相当于看板）

轻量追踪每页状态：

```markdown
# 制作进度

## 当前阶段
首版制作

## 页面状态
| 页码 | 内容概要 | init | 选择 | rev1 | 选择 |
|------|---------|------|------|------|------|
| 01   | 封面    | done | v2   |      |      |
| 02   | 引言    | done | v3   |      |      |
| 03   | ...     | wip  |      |      |      |
```

只记录页码、状态、用户选择。详细内容在制作记录里。

### 3. 制作记录 — 变更日志（相当于 Changelog）

每页完成时写一份记录，包含：
- 页码和内容主题
- 完整 Prompt
- 参考图信息
- 3 张候选图各自的特点
- 用户选了哪张、原因
- 迭代过程

记录分两个目录：
- 首版制作 → `ppt-pages/制作记录/首版/XX.md`
- 修改 → `ppt-pages/制作记录/修改/revN-XX.md`

**这是最有价值的文档**——它记录了你的决策链。为什么选了方案 B 而不是 A？当时的考量是什么？三个月后再看，你仍然知道为什么。

## Git 使用规范

### 提交粒度：按页面

```bash
# Good：一个 commit 只涉及一页
git commit -m "第05页首版：冰面爆裂+光芒凝聚凤凰"

# Bad：多页混在一起
git commit -m "更新了好几页PPT"
```

### 提交内容：只加相关文件

```bash
# Good：精确指定文件
git add ppt-pages/05/init/gen.py \
        ppt-pages/05/init/v1.png \
        ppt-pages/05/init/v2.png \
        ppt-pages/05/init/v3.png \
        ppt-pages/制作记录/首版/05.md \
        progress.md

# Bad：全量添加
git add -A  # 会把其他页未完成的文件也带进来
```

### Commit Message 格式

- 首版：`第XX页首版：内容概要`
- 修改：`第XX页修改(revN)：改动概要`

### Git 历史的价值

项目结束后，`git log --oneline` 就是一份完整的项目进度表，一眼就知道做了什么、先做后做的顺序、每页迭代了几轮。

## AI 协作的边界

| 角色 | 职责 |
|------|------|
| **人** | 定需求、选图、做决策、确认最终效果 |
| **AI** | 写 Prompt、写 gen.py、执行生成、写制作记录、Git 提交、分析问题提建议 |
| **AI 不做** | 替人做选图决策、跳过用户确认、自作主张修改其他页 |

这个边界很重要：**AI 是工具，不是甲方**。它可以建议"我觉得方案 B 更好，因为…"，但最终决策权在人。
